## Setup and deployment prerequisites

1. Confirm the intended Supabase project and hosting owner. Record the checkout,
   reviewed SQL hashes, environment/configuration owner and recovery contacts in
   a private operating ledger. Keep account credentials outside this repository.
2. Back up the existing database and separately protect original private file
   bytes. Verify the operator can restore both into an isolated project before
   a live upgrade. An SQL dump alone is not proof of Auth or Storage recovery.
3. Existing databases: follow the [consolidated update guide](supabase/INSync_Consolidated_Update_README.md)
   and [inspection runbook](supabase/RUNBOOK.md). Run the entire guarded
   [INSync_Consolidated_Update.sql](supabase/INSync_Consolidated_Update.sql)
   manually as trusted `postgres`, after inspection/rehearsal. It covers final
   M01–M04/M06–M08/M10–M13 definitions; M05/M09 remain separate reviewed
   historical validation gates. Do not replay successful original migrations.
4. An already verified M11 catalog can instead receive reviewed
   [M12_handover_workflows.sql](supabase/migrations/M12_handover_workflows.sql).
   Verify exact existing definitions first. Do not choose a route by filename
   presence alone. M12 installs four protected user-facing RPCs, the single-current-year
   index and controlled year-marker permissions. It also preserves known raw
   version-zero metadata prospectively when a real replacement succeeds. This
   is an unverified snapshot, not an invented committed version/review; no
   historical attendance/document/evaluation backfill is performed.
5. A genuinely new empty project follows [WEB_SETUP.md](WEB_SETUP.md): seed-free
   initial schema, then reviewed M01–M12 in order. Do not use the initial schema
   on an existing database. Never run the destructive legacy `schema.sql`, test
   fixtures or operational cleanup as installation/upgrade steps.
6. Resolve conflicting current years explicitly before updating. Inspect:
   `SELECT y.id,y.label,y.is_current,to_jsonb(y)->>'archived_at' AS archived_at FROM public.academic_years y ORDER BY label;`
   An authorized operator chooses the actual active year in a separately
   reviewed transaction; do not infer it from labels, dates or latest creation.
   After migration, Admin can configure it through Master Data. No automatic
   rollover or historical cohort assignment is introduced.
7. Use Node >=22.12, the committed lockfile and `npm ci`. Configure the existing
   `.env` from `.env.example` with only public `VITE_SUPABASE_URL` and
   `VITE_SUPABASE_ANON_KEY`. Never put a secret/service-role key in a browser
   variable. This work preserved existing environment files and the added CLI
   dependency. Validate project/key connectivity separately; format checks do
   not authenticate configuration.
8. Build with `npm run build`; configure an HTTPS static host with SPA fallback.
   Route/query/hash handling must allow Auth callbacks at the same app path.
   Publish/deploy only after separate authorization. Clear old clients after
   database and client versions are coordinated. The current chunk-size warning
   remains a performance consideration, not a passed load-time guarantee.

## Auth, email and Storage configuration

The SDK retains session persistence, refresh and callback handling. Operator
setup is still required:

- Set Auth Site URL to the intended app URL. Allow the exact password-recovery
  redirect generated by the app: the same origin/path plus `?auth=recovery`.
  Configure corresponding approved local/staging URLs separately. Match the
  installed email template/flow and avoid broad production redirect wildcards.
- Verify the chosen email-confirmation setting, confirmation redirect, SMTP
  sender identity, delivery and password-recovery email/link expiry on a
  disposable project. Registration instructions follow the returned session:
  confirmation does not activate an account. Recovery changes only the password.
- Keep the `documents` bucket private, 10 MiB maximum, PDF/JPEG/PNG. Confirm
  provider-generated object metadata contains actual MIME/size values expected
  by finalization. Confirm RLS/grants and old permissive policies match the
  reviewed catalog. Test original file delivery, signed-link expiry and abandoned
  staging cleanup through the Storage API on disposable files. Never delete
  provider Storage metadata with SQL to remove bytes.
- Use the [official recovery API](https://supabase.com/docs/reference/javascript/auth-resetpasswordforemail),
  [password update API](https://supabase.com/docs/reference/javascript/auth-updateuser)
  and [redirect guide](https://supabase.com/docs/guides/auth/redirect-urls) when
  configuring/testing actual Supabase behavior. Local mocks do not prove delivery.

## Accounts and Administrator operations

Public registration requests an **Intern/Pending** account only. School and
student ID follow existing field requirements; email/password/name are required.
The database owns the effective role/status. Email confirmation and Admin
activation are separate. Pending/Inactive users cannot access internship data.

Provision the first Admin using the exact Auth-verified UUID and trusted operator
procedure in [WEB_SETUP.md](WEB_SETUP.md); do not use guessed identifiers or
public registration metadata. Subsequent staff can register, then an authorized
Admin changes their role/status in Account Management. Roles are Admin,
Instructor (including OJT Coordinator) and Intern. There is no Supervisor role.
Keep another authorized Admin available before restricting the operating Admin;
the system does not promise last-Admin lockout prevention.

Admin walkthrough:

1. **Overview:** inspect real account/directory totals and recent trusted/legacy
   audit events. Retrieval errors mean Unavailable and offer Retry.
2. **Account Management:** search/filter/page accounts; edit name, role and
   status, then save. Activate a Pending Intern explicitly. Resolve assignments
   before staff demotion/deactivation; remove Instructor assignment before an
   Intern becomes staff. Extensions and prior records are retained.
3. **Interns:** select an active Instructor, company and section; enter saved
   target hours (>0, <=10,000, two decimal places) and Save. Attach missing
   standard requirements. **Manage requirements** adds custom requirements
   with distinct identities even when labels repeat. Creation has a retry UUID;
   after an unknown outcome, Refresh before changing the attempted name.
4. **Master Data:** create/edit companies, sections and year labels. **Set
   current year** asks for confirmation and uses a serialized expected-current
   RPC. It changes only the marker. Inspect archive impact, type ARCHIVE and
   confirm eligible archival; retain links/history. Current years cannot be
   archived. Set a replacement explicitly first.
5. **Bulk Import:** download blank student/instructor planning templates in
   CSV or genuine XLSX. Import/provisioning is disabled; templates create no
   accounts. Use individual onboarding until the proposal below is approved.
6. **Audit Logs:** filter the entire server history, page and retry. PDF/XLSX/CSV
   report buttons use matching filters, not the visible page. **Export all audit
   CSV** retains its separate unfiltered complete-history semantics. Trusted
   database provenance is distinct from preserved legacy/unverified events.
7. **Backup & Security:** informational permissions only. Backup status and
   uptime are not connected; verify them outside this app.

## Instructor / OJT Coordinator walkthrough

1. **Class Dashboard:** complete assigned-roster totals; combine search/section
   filters and pagination for the list. Click Cleared or At Risk for matching
   interns/reasons. Cards count distinct complete assigned-roster IDs, retain
   Unknown counts and explain the existing rule.
2. **Progress Tracker:** inspect logged and verified hours against each saved
   target. Unknown evidence is not zero or completion. Focus/visible-minute
   refresh updates metadata; refresh is not a live subscription guarantee.
3. **Evaluations:** select an assigned Intern, rate all four criteria 1–5 and
   submit feedback. Server weights are 25/35/20/20; the stored authoritative
   overall score is shown. Preserve failed drafts and use date/history filters.
4. **DTR Review:** inspect closed attendance, accomplishments and evidence;
   **Verify hours** authorizes trustworthy closed records only. Ordinary clock-out
   remains unverified. Legacy/invalid intervals use corrections. Review Pending
   corrections, inspect overnight dates and provide a rejection explanation.
   Expected instants/assignment changes prevent stale verification.
5. **Intern Documents:** review signed current files; approve or request revision
   with an explanation, or revoke a current approval through its supported flow.
   Replacements reset current review and retain versions/events. Review flexible
   file sets separately; first legacy replacements additionally retain original
   saved file/review metadata as explicitly unverified. Existing pre-capture
   metadata that was already lost cannot be reconstructed without actual evidence.
   Flexible approval never contributes to clearance.
6. **Reports:** use its assigned-roster search/section filters and date range;
   full matching assigned roster, not just the current page. Date
   range affects dated records; lifetime evidence determines current clearance
   and D13 risk. Download class progress, evaluations, clearance eligibility or
   risk in PDF/XLSX/CSV. Eligibility is not certificate issuance.
7. **Announcements:** choose an individual or assigned active roster; submit
   a subject/body. New recipients are frozen at send time. Reassignment does
   not add recipients to an old announcement. Test only fixture recipients.

## Intern walkthrough

1. **My Dashboard:** assigned company/Instructor, saved target, verified progress,
   logged hours, charts, evaluations and intended announcements. Unknown input
   produces truthful unavailable/Unknown output.
2. **My Attendance:** clock in; enter accomplishments at clock-out. Logged hours
   do not become verified automatically. Filter Manila calendar periods; submit
   a correction with explicit end date when overnight. Review status/explanations
   and retain failed drafts. The existing all-record informational DTR CSV stays
   available here.
3. **My Documents:** use the requirement dropdown; repeated labels remain distinct
   IDs. Upload/replace the chosen standard/custom requirement. Accepted formats
   and limits are shown; original files/history remain private. Use unfinished
   upload recovery after ambiguous outcomes. Flexible sets accept 1–10 files,
   <=10 MiB each, <=50 MiB total; title required, description optional. Revise
   and resubmit as requested. They remain outside the clearance checklist.
4. **My Evaluations:** read server-scored criteria and feedback; select date
   ranges. Interns cannot submit/edit evaluations.
5. **Reports:** choose All records or inclusive custom Manila dates; export DTR,
   performance, Monday–Sunday weekly hours or the document/version register as
   PDF/XLSX/CSV. Use My Documents for original uploaded file downloads. The
   register does not fabricate a ZIP archive or alter original submitted files.
6. Sign out and test reload/session restoration. **Forgot password?** requests
   a conditional recovery email; a valid link opens the password form before
   role routing. Failure retains input; success returns to sign-in without
   changing approval/role.

## Report contract and limitations

PDF and XLSX carry the INSync logo/title, saved institution when available,
relevant account/Intern details, filters/range, Manila generation timestamp,
labelled tables, totals and page numbering. CSV carries textual branding and
metadata. Every format says it is informational and not institutional
certification. No seals, signatures, official approval wording or policies are
invented. XLSX student IDs are typed text and hours/scores are numeric when
known; CSV uses formula-safe literals, but import IDs as text in spreadsheet
software to retain leading zeros (CSV itself has no column-type metadata).

Retrieval is exact-count/keyset checked across API pages, bounded at 50,000 rows
per source table. Detected caps/errors stop downloads. This is not an atomic
database snapshot; equal-count concurrent edits can still occur. PDF supports
5,000 table rows and the bundled Unicode font; unsupported characters or larger
PDFs produce an explicit error—use full XLSX/CSV. Classification exports list
Unknown interns separately from confirmed qualifying counts. No missing evidence
is inferred as approval, verified hours, an official certificate or zero risk.

Clearance uses lifetime verified hours against the saved target, all four types
(MOA, Endorsement, Consent, Medical) and valid current approval of **every**
standard/custom requirement. The existing documented D13 risk rule is retained:
known verified-hours shortfall plus a Needs Revision requirement or at least
seven Manila calendar days since last valid closed attendance. No saved deadline
exists and no new deadline policy was introduced; lack of sufficient evidence
remains Unknown. See [card implementation](INSTRUCTOR_CARD_IMPLEMENTATION.md).

## Support and acceptance checklist

For missing RPC/table or schema-cache errors, compare the actual catalog with
the consolidated guide's verification queries and private migration ledger.
Apply only reviewed missing effects, then verify `NOTIFY pgrst,'reload schema'`
from the successful transaction. Stop on schema/ownership/data drift; do not
delete history, bypass guards or expose private storage. If SQL fails before
commit, execute ROLLBACK when needed and inspect the first error.

For upload failures, preserve receipts/files until the existing recovery RPC
confirms the outcome. For sign-in/recovery, verify Auth settings/redirects/email
delivery and account status separately. For Unknown metrics, inspect invalid
timestamps/current evidence and request supported correction/resubmission; do
not guess historical reviewers, dates or hours. Preserve failed drafts and Retry.

Owner acceptance must be recorded on a **separately authorized disposable
Supabase project and test accounts**, then repeated at the deployed URL after
separate deployment authorization:

- [ ] Repository revision, reviewed SQL hash, database baseline/ledger accepted.
- [ ] Backup and isolated restore of database, Auth identity and private files proven.
- [ ] Catalog/RPC grants/RLS/Storage policies match; M12 installed; cache refreshed.
- [ ] Confirmation-on/off instructions, real email delivery, recovery expiry,
  session reload/expiry and logout accepted.
- [ ] Pending signup → explicit Admin activation → Intern access accepted.
- [ ] Role restrictions, assignment/status changes and cross-account direct API
  denials tested independently of UI visibility.
- [ ] Company/section/Instructor and fractional target saved; manual year switch
  and archive impact preserve historical links.
- [ ] Clock/accomplishment/unverified close → explicit verification or correction
  review; overnight dates and rejection/failed drafts accepted.
- [ ] Standard/custom upload → revision → replacement → approval/history; private
  signed-link delivery/expiry and ambiguous cleanup accepted.
- [ ] Flexible multi-file finalization/review remains separate from clearance.
- [ ] Four-criterion server score → read-only Intern result accepted.
- [ ] Individual/roster announcement delivered only to intended fixture recipients,
  including reassignment; no messages to real users for testing.
- [ ] Clearance/risk and Unknown evidence update after hours, versions, targets
  and assignments change.
- [ ] All report categories/filters/ranges export complete authorized matching
  records across pages; XLSX IDs/text, totals and PDF pagination accepted.
- [ ] All 19 role destinations, mobile navigation, keyboard/focus, short-screen
  auth scrolling and target browsers/devices accepted.
- [ ] Exclusions/proposals, backup/monitoring responsibilities and support owner
  signed off in an acceptance record. No guarantee is inferred from local tests.
